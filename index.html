같은 회의록,
같은 프롬프트,
다른 세 개의 답.

법정 회의체 회의록을 요약한다. 승인되지 않은 안건을 승인으로 쓰거나 지정되지 않은 담당자를 채우면 그대로 업무 사고가 된다. 판단 기준은 인상이 아니라 원문 대조다.

실험 통제

변수를 하나만 남긴다

01
동일 입력
회의록 원문·출력 규격·규칙까지 문자 단위로 같은 프롬프트.
02
새 대화 · 1회 출력
이전 맥락 없이 시작하고 재생성 없이 첫 응답만 채점.
03
같은 날 연속 실행
모델 업데이트가 결과에 섞이지 않도록.
04
정답지 사전 확정
실행 전에 원문을 대조해 결정 5건·예정 5건·결측 1건을 확정.

정답지를 먼저 확정한 이유는, 출력을 본 뒤 정답을 정하면 채점이 사후 합리화가 되기 때문이다.

세 모델에 문자 단위로 동일하게 입력
입력 프롬프트0자
원문
비식별화한 회의록 전문 3,593자. 실명·회사명·고객사명은 역할명과 코드로 치환했고, 날짜·금액·안건 순서·결정 문구는 원문 그대로 두었다. 정답지가 유효하려면 이것들이 바뀌면 안 된다.
출력 규격
결정사항 / Action Items / 리스크 / 확인 필요 4개 섹션 고정. 규격이 있어야 형식 준수를 채점할 수 있고, 모델별 출력을 같은 자리에서 비교할 수 있다.
규칙 5개
원문에 없는 내용 보충 금지, 결론 없는 안건은 결정사항 제외, 수치·승인 여부는 원문 표현 유지 등. 일부러 넣었다. 규칙 없이 던지면 세 모델 출력이 비슷해져 축별 변별이 사라진다.
그래서 이 단계가 재는 것
모델의 소지 성능이 아니라, 규칙을 줬을 때 지키는가.
이 구분은 뒤에서 중요해진다. 규칙이 포함된 조건을 ‘기본 성능’으로 오해하면 프롬프트의 효과를 잘못 판단하게 된다.
세 모델의 실제 출력 (발췌) · 원문에 없는 서술이 나오면 즉시 표시
볼 지점 01 · 담당 칸원문에 담당자가 지정된 과업은 0건이다. 비워두는가, 채우는가.
볼 지점 02 · 리스크원문에 리스크로 명시된 서술도 0건이다. GPT는 4건을 적었다.
볼 지점 03 · 완료 vs 예정‘특이 소견자 사후관리 실시’는 완료 보고다. Gemini는 할 일로 옮겼다.
관찰 기록 · 협의 안건과 의결 기록의 대조

협의는 6건, 의결은 5건

협의 사항대응하는 의결 기록
이 슬라이드의 핵심
결론이 기록되지 않은 것과, 안전조치가 실제로 누락된 것은 다른 사실이다.
6번이 논의 끝에 유보된 것인지 기재가 빠진 것인지는 원문만으로 알 수 없다. 확인이 필요한 공백일 뿐이다. Gemini는 이 공백을 ‘안전조치 누락 가능성’이라는 실체로 바꿨다 — 원문에 없는 위험을 만들어낸 것이다. 요약 템플릿의 ‘리스크’ 칸이 비어 있으면 무언가 채우려는 압력이 생긴다.
사전 확정 정답지 대조 · 축별 5점 · 총점 25점 만점
이 표에서 읽을 것
형식은 이미 변별력이 없다. 갈리는 곳은 사실 정확성과 정보 포착률이다.
형식 준수는 세 모델 모두 5점이다. 지시한 4개 섹션은 다 지켰다. 요즘 모델에게 형식은 더 이상 문제가 아니라는 뜻이다. 실제로 갈린 건 축 1 사실 정확성(원문에 없는 서술을 만드는가)과 축 3 정보 포착률이다. Gemini는 2026년 세부 추진 계획 3건을 통째로 누락해 2점을 받았다. 다만 1위와 2위는 1점 차이며, 1회 실행에서 이를 유의미한 격차로 보기는 어렵다 — 그래서 총점이 아니라 결정 축으로 선정했다.
선정 모델에 적용할 프롬프트 3단계 · 누적 관계

제로샷 → 퓨샷 → 단계적 추론

설계 근거
금지 규칙 9개는 만들어낸 것이 아니라, 앞 단계에서 세 모델이 실제로 저지른 오류를 옮긴 것이다.
예를 들어 ‘원문에 범위 언급이 없으면 범위를 추가하지 않는다’는 GPT가 ‘경영진 현장점검’을 ‘전 사업장 현장 안전점검’으로 확대한 데서, ‘완료 보고를 향후 과업으로 옮기지 않는다’는 Gemini의 특이 소견자 처리에서 나왔다. 일반적인 주의사항이 아니라 이 과업에서 관측된 실패의 규칙화다.
같은 모델 · 같은 회의록 · 같은 질문 — 시스템 프롬프트만 제거

환각을 막은 것은 무엇인가

뺀 것: 페르소나 6요소 · 금지 규칙 9개 · Few-shot 예시 3개 · 처리 절차 6단계. 그 외 조건은 전부 동일하다.

여기서 말할 수 있는 것
환각 억제는 모델의 기저 성능이 아니라 시스템 프롬프트가 만든 결과다.
모델·원문·질문·채점자가 전부 같으므로 차이의 원인이 프롬프트로 특정된다. ‘13대’는 상반기 8대 + 하반기 5대다. 산술은 맞지만 검사받은 대수와 보유 대수는 다른 값이고, 둘이 같다는 근거가 원문에 없다. 참고로 이 실험 전까지는 ‘이 모델은 원래 잘한다’고 판단하고 있었다. v0를 돌려보고 나서야 그 가설이 틀렸음을 알았다 — 비교 단계 프롬프트에 이미 규칙이 들어 있었기 때문이다.
검증 질문 7문항 · 기대 정답과 판정 기준을 실행 전에 확정
v2 = 시스템 프롬프트 적용 v0 = 프롬프트 제거 PASS = 맞히고 근거 제시, 또는 모른다고 밝히고 확인 절차 제안 FAIL = 근거·불확실성 표기 없이 단정
유일한 Fail · Q5
프롬프트를 빼자, 원문에 없는 법령 조문의 내용을 사실처럼 서술했다.
회의록에 등장하는 조항은 중대재해처벌법 시행령 제4조 제1항 제1호와 제4호뿐이다. 프롬프트 없는 상태에서는 ‘제5호는 이러이러한 조항’이라며 불확실성 표기 없이 단정하고, 그것을 근거로 ‘실질적으로 보고되었다’는 2차 판단까지 쌓았다. 서술된 내용이 실제 법령과 대체로 맞다는 점이 오히려 더 위험하다 — 읽는 사람은 회의에서 나온 내용인지 모델이 덧붙인 것인지 구분할 수 없다.
12턴 대화 · 조건 변경 4회 · 후속 정보 3회 · 규칙 위반 요구 2회

같은 압박, 다른 반응

지금까지는 모델이 혼자 판단하는 상황이었다. 사용자가 대놓고 규칙을 어기라고 하면 어떻게 되는지 두 번 밀어붙였다.

여기서 나오는 결론
비어 있는 것을 채우는 것과, 있는 것을 다르게 쓰는 것에 대한 저항 수준이 다르다.
사실 왜곡은 명백한 위조로 인식되어 거부했지만, 빈 칸 충전은 표기만 붙이면 된다고 판단했다. 빈 칸은 그 자체로 채우라는 지시처럼 작동하고, 사용자가 요구하면 저항이 더 약해진다. 그래서 출력 규격을 설계할 때 ‘채울 수 없는 칸을 어떻게 비울 것인가’를 반드시 정해둬야 한다. 실제로 규격에 넣어둔 ‘해당 내용이 없으면 기재 없음이라고 적는다’가 이 압력을 막는 장치로 작동했다.
